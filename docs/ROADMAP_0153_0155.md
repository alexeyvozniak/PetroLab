# PetroLab 0.15.3–0.15.5: implementation specification

Status: active implementation plan.

Version note: while this work was being implemented, PetroLab 0.15.2 was released separately with amphibole diagnostics and Windows-CI cleanup. The three milestones below therefore moved forward by one version without changing their scope.

## Product goal

Bring three underdeveloped workflows to the same standard as the mineral workflow:

1. publication-ready multi-panel figure composition from arbitrary plots/images;
2. grain-profile plotting as a first-class scientific plot mode;
3. a modern whole-rock workspace centered on samples, series and interpretation rather than raw edit forms.

All three features must reuse exact object identities and existing provenance/style systems. No workflow may silently broaden a selection, replace missing chemistry by zero, or infer physical identity from a display label.

---

# v0.15.3 — Publication Figure Composer

## User story

A researcher selects 2–12 existing plots or images, arranges them into one publication figure, receives automatic panel labels, can edit/hide/move individual labels, and exports a journal-ready figure.

## Panel sources

Required in the first release:
- uploaded PNG, JPEG, TIFF and WEBP images;
- PetroLab-generated plots passed directly through session state without download/re-upload;
- saved analytical images;
- saved rock photographs;
- saved thin-section images through a common source adapter.

Later extension:
- direct reuse of saved plot recipes as vector panels;
- direct SVG panel ingestion where the local renderer supports it safely.

## Layout

Presets and custom layouts:
- 1×2, 1×3, 2×2, 2×3, 3×2, 3×3;
- automatic grid based on panel count;
- custom 1–4 columns for up to 12 panels.

Each panel stores:
- immutable source id and display name;
- order;
- crop mode: contain / cover;
- optional title/caption;
- panel-label text;
- label enabled flag;
- label x/y in normalized panel coordinates;
- horizontal/vertical alignment;
- font size and weight.

## Automatic panel labels

Built-in sequences:
- Latin uppercase: A, B, C, D…;
- Latin lowercase: a, b, c, d…;
- Cyrillic uppercase: А, Б, В, Г, Д, Е…;
- Cyrillic lowercase: а, б, в, г, д, е…;
- no labels.

Rules:
- labels are generated from panel order;
- changing the suggested alphabet must not overwrite manually edited labels;
- a manual “reset labels” action regenerates the sequence;
- every label can be disabled independently;
- a global switch can hide/show all labels;
- x/y position is editable per panel;
- labels may be moved slightly outside the 0–1 panel bounds when needed;
- exported labels are part of the figure itself, not a Streamlit-only overlay.

## Journal presets and export

Composer reuses `FIGURE_PRESETS` for width, font family, base font size and publication defaults. The user can override layout dimensions.

Required export:
- PNG 300/600 dpi;
- SVG;
- TIFF 300/600 dpi;
- deterministic JSON recipe describing source IDs, order, layout and labels.

## Safety requirements

- panel order remains stable across reruns;
- EXIF orientation is normalized;
- a broken panel source produces an explicit broken-source cell and never shifts later panels/labels;
- unused grid cells remain blank and never receive phantom labels;
- generated PetroLab figures are content-hash de-duplicated in the composer inbox;
- a missing linked thin-section original may use a stored preview only with an explicit user warning.

## Acceptance tests

1. Six Latin panels export A…F exactly once.
2. Six Cyrillic panels export А…Е with the correct sixth Cyrillic symbol.
3. A custom label survives reruns and recipe export.
4. A disabled label is absent while neighboring labels remain.
5. Moving one label changes only that panel.
6. Five panels in a 2×3 layout leave one blank unlabelled cell.
7. A broken image does not move the label or source identity of the following panel.
8. Existing scientific multi-panel figures embed the same editable panel-label model.
9. Windows CI and existing exact-selection regressions remain green.

# v0.15.4 — Grain Profile Mode

## User story

A researcher selects 5–100+ analyses through one grain and plots compositional change from core to rim or along an analytical traverse.

## Entry points

- `Исследование → Профиль по зерну` as a dedicated mode;
- direct action from an exact global-search result;
- later: action from a grain/thin-section physical object.

## Exact selection

The profile stores and operates on exact `analysis_id` values. Requested IDs that disappear from the active selection are an error, not silently dropped rows.

## Profile ordering

Supported x-axis modes:
1. current exact-selection order;
2. explicit numeric order column;
3. numeric point index parsed from a chosen label column (`P-1`, `P-2`…);
4. measured distance column, e.g. µm;
5. normalized distance 0–1;
6. geometry-derived cumulative distance from x/y coordinates.

Geometry rules:
- coordinates may be used only when every point has one identical non-empty coordinate-frame/image identifier;
- traverse order must still be explicit;
- PetroLab must never connect coordinates from different images by proximity or matching labels.

## Y series

The user can select one or multiple numeric fields:
- oxides;
- trace elements;
- APFU values;
- derived indices such as Mg#, Cr#, Ti#;
- materialized ratios.

Missing values remain `NaN` and produce graph gaps rather than zero values.

## Zones and direction

- optional core / mantle / rim zones;
- arbitrary named intervals;
- reverse core↔rim direction;
- optional normalized distance;
- zone boundaries stored in the recipe.

## Multiple grains

Later extension:
- overlay multiple grains on a common normalized x-axis;
- facet grains into aligned panels;
- no averaging unless explicitly requested.

## Image-linked traverse

Later extension:
- choose one calibrated image of a grain;
- draw/select a traverse;
- attach ordered analytical points;
- show image and profile together.

## Export

- SVG;
- PNG 600 dpi;
- XLSX containing exact selected rows in profile order;
- JSON recipe containing analysis IDs, order rule, direction, zones and selected variables.

## Acceptance tests

1. Five-point and 100-point profiles preserve exact identity/order.
2. `P-5` is interpreted as point number 5, not negative five.
3. Reversing direction reverses identities and re-zeros distance consistently.
4. Missing chemistry remains a graph gap.
5. Duplicate explicit order fails visibly.
6. A requested missing analysis ID fails visibly.
7. Geometry across different or blank image/frame IDs is rejected.
8. Existing search exact-selection guarantees remain intact.

# v0.15.5 — Modern Whole-Rock Workspace

## Product problem

The existing `Породы` implementation contains useful editing and plotting functions but is form-centric. The primary user path must become an object workspace comparable to the mineral workflow while preserving the mature editor as a technical editing surface.

## Information architecture

### Level 1: Rock workspace / overview

Header:
- rock/sample name;
- massif/complex;
- lithology;
- locality;
- age ± uncertainty and method;
- data-health badges.

Quick actions:
- compare/build whole-rock diagrams;
- edit/add data for this exact rock;
- later: normalized trace pattern, export sample card.

Overview cards:
- major-element completeness;
- recognized trace-element count;
- isotope systems present;
- linked mineral datasets;
- photos;
- warnings/QC.

### Level 2: Data tabs

Tabs:
1. Overview;
2. Whole-rock chemistry;
3. Trace elements;
4. Isotopes;
5. Mineral links;
6. Images;
7. Diagrams;
8. Provenance / interpretation.

The overview is read-oriented. Editing remains in the established rock editor until each editing workflow is migrated safely.

## Whole-rock data health

For the initial overview, major completeness expects:
- SiO2, TiO2, Al2O3, MnO, MgO, CaO, Na2O, K2O, P2O5;
- plus one recognized total/split iron representation.

Trace elements are identified through the canonical column schema, not by raw string guessing. Units remain explicit and wt.% is never silently mixed with µg/g.

Warnings include:
- missing whole-rock chemistry;
- incomplete major components;
- no recognized trace elements;
- no isotope data;
- no linked mineral datasets;
- no rock photograph;
- missing chemistry provenance/source.

## Whole-rock plotting

First-class plot families, reusing established backends:
- TAS and alkaline/subalkaline classification where valid;
- Harker diagrams;
- Mg# and compatible-element screening;
- REE and multi-element normalized patterns;
- isotope plots where meaningful;
- literature comparison using consistent source visibility controls.

## Series/group workflow

A rock must be usable both as an individual sample and as part of a series:
- dyke swarm;
- massif/complex;
- lithological group;
- publication/reference series;
- user-defined work group.

Group visibility and style reuse the common plot-style system.

## Provenance

Each composition/isotope row keeps source, method and laboratory metadata. Bulk import must never collapse incompatible duplicates silently.

## Acceptance tests

1. Workspace rejects a rock from another project.
2. Complete and incomplete major chemistry produce correct health state.
3. Trace elements are counted through canonical semantics and keep their units.
4. Isotope systems, photos and linked mineral datasets are surfaced without navigation loss.
5. Workspace → editor opens the exact rock by ID.
6. Existing rock-regression tests remain green.
7. Whole-rock + literature filtering continues to use provenance/source controls.

# Shared architecture

## Immutable selections

Use exact identities rather than display names whenever possible:
- analysis IDs for analytical points;
- rock IDs for whole-rock samples;
- image IDs / generated content-hash source IDs for figure panels.

Display names are metadata, not identity.

## Recipe model

Each publishable output is reproducible from a versioned JSON-compatible recipe.

Common recipe fields:
- `recipe_version`;
- `kind`;
- selected object IDs;
- ordering;
- layout;
- styles;
- journal preset;
- output settings.

## Definition of done

A version is not done merely because its page renders. It is done only when:
- feature-specific regression tests are green;
- exact-selection / project-scope regressions are green;
- full Windows verification is green;
- publication/export regression is green where applicable;
- no workflow silently guesses identity or missing chemistry;
- the feature is exposed through a natural user-facing route.
