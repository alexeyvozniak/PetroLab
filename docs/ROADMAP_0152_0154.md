# PetroLab 0.15.2–0.15.4: implementation specification

Status: active implementation plan

## Product goal

Bring three underdeveloped workflows to the same standard as the mineral workflow:

1. publication-ready multi-panel figure composition from arbitrary plots/images;
2. grain-profile plotting as a first-class scientific plot mode;
3. a modern whole-rock workspace centered on samples, series and interpretation rather than raw edit forms.

The three features must reuse one selection/provenance model and one publication-style system. No workflow may silently broaden a user selection or infer physical identity from display labels.

---

# v0.15.2 — Publication Figure Composer

## User story

A researcher selects 2–12 existing plots or images, arranges them into one publication figure, receives automatic panel labels, can edit/hide/move individual labels, and exports a journal-ready figure.

## Scope

### Panel sources

Phase A (v0.15.2):
- uploaded raster images: PNG, JPEG, TIFF, WEBP;
- PetroLab-generated raster exports passed through session state;
- saved rock/sample/thin-section images through a common panel-source adapter.

Phase B:
- direct reuse of saved PetroLab plot recipes as vector panels;
- direct SVG panel ingestion where the local renderer supports it safely.

### Layout

Presets:
- 1×2, 1×3, 2×2, 2×3, 3×2, 3×3;
- automatic grid based on panel count;
- custom row/column count.

Each panel stores:
- source id/name;
- order;
- crop mode: contain / cover;
- optional title/caption;
- panel label text;
- panel label enabled flag;
- panel label x/y in normalized panel coordinates;
- horizontal/vertical alignment;
- font size and weight.

### Automatic panel labels

Built-in sequences:
- Latin uppercase: A, B, C, D…;
- Latin lowercase: a, b, c, d…;
- Cyrillic uppercase: А, Б, В, Г, Д, Е…;
- Cyrillic lowercase: а, б, в, г, д, е…;
- no labels.

Rules:
- labels are generated by panel order;
- generation never overwrites a manually edited label unless the user explicitly resets labels;
- every label can be disabled independently;
- a global switch can hide/show all labels;
- x/y position is editable per panel in normalized coordinates;
- default position is top-left inside the panel;
- exported labels must be part of the figure, not an external UI overlay.

### Journal presets

Composer reuses `FIGURE_PRESETS` for:
- final figure width;
- font family;
- base font size;
- output DPI.

Additional composer presets may specify:
- default label alphabet and case;
- default panel-label size;
- inter-panel spacing;
- background.

The user must always be able to override the preset.

### Export

Required:
- PNG 300/600 dpi;
- SVG;
- TIFF 300/600 dpi when Pillow supports target mode;
- JSON recipe describing layout and labels.

The recipe must be deterministic and round-trippable.

### Safety/quality requirements

- panel order must remain stable across Streamlit reruns;
- image EXIF orientation must be normalized;
- a broken panel source must fail visibly and must not shift labels to another panel;
- output dimensions must be deterministic from preset + grid;
- unused grid cells must remain blank and must not receive labels;
- label sequence generation must be tested beyond six panels.

### Acceptance tests

1. 6 panels + Latin uppercase => A…F exactly once.
2. 6 panels + Cyrillic uppercase => А…Е plus the sixth sequence symbol according to the defined alphabet.
3. custom label on panel 3 survives rerun and export.
4. disabled panel 2 label is absent from SVG/PNG while other labels remain.
5. moving panel 4 label changes only panel 4.
6. 5 panels in a 2×3 layout leave one blank cell with no phantom label.
7. output works on Windows CI with Arial fallback behavior unchanged.

# v0.15.3 — Grain Profile Mode

## User story

A researcher selects 5–100+ analyses through one grain and plots compositional change from core to rim or along an analytical traverse.

## Entry points

- `Plots → Grain profile` as a dedicated mode;
- action from a selected analysis group / grain / thin-section point set;
- action from search results without losing the exact analysis-id selection.

## Profile ordering

Supported x-axis modes:

1. explicit point order column;
2. numeric point index parsed from a chosen label column;
3. measured distance column in µm;
4. normalized distance 0–1;
5. geometry-derived cumulative distance from x/y coordinates when coordinates are in one calibrated frame.

PetroLab must never infer a geometric profile across unrelated images. Geometry-derived distance is allowed only when all selected points share one coordinate frame/calibration.

## Y series

The user can select one or multiple numeric fields:
- oxides;
- trace elements;
- APFU values;
- derived indices such as Mg#, Cr#, Ti#;
- ratios already materialized or explicitly defined in the plotting workflow.

## Zones and direction

- optional core / mantle / rim zones;
- arbitrary named intervals;
- reverse direction button;
- zone boundaries stored in profile recipe;
- zone shading optional.

## Multiple grains

- overlay multiple grains with a common normalized x-axis;
- or facet them into aligned panels;
- no averaging unless explicitly requested.

## Image-linked profile

Later minor release:
- choose one image of a grain;
- draw/select a traverse;
- attach ordered analytical points to it;
- preview image and profile together.

## Export

- SVG / PNG 600 dpi;
- XLSX exact selected rows in profile order;
- JSON recipe with analysis ids, order rule and selected variables.

## Acceptance tests

- 5-point and 100-point profiles preserve exact ordering;
- reversing direction reverses x/order only, not data identities;
- missing values create gaps rather than zeroes;
- `<DL` values remain qualified/missing according to measurement policy;
- exact analysis-id selection survives reruns;
- geometry mode refuses points from different image coordinate frames.

# v0.15.4 — Modern Whole-Rock Workspace

## Product problem

The current `Породы` page is functionally rich but interaction is form-centric. It must become an object workspace comparable to the mineral workflow.

## New information architecture

### Level 1: Rock workspace / overview

Header:
- sample/rock name;
- massif/complex;
- lithology;
- locality;
- age ± uncertainty and method;
- data-health badges.

Quick actions:
- compare with literature;
- open whole-rock diagrams;
- normalize trace-element pattern;
- link mineral datasets;
- open images;
- export sample card.

Overview cards:
- major-element completeness;
- trace-element completeness;
- isotope systems present;
- linked mineral datasets;
- photos;
- warnings/QC.

### Level 2: Data tabs

Tabs:
1. Overview;
2. Whole-rock chemistry;
3. Trace elements / normalized patterns;
4. Isotopes & geochronology;
5. Mineral links;
6. Images;
7. Interpretation / notes;
8. Provenance.

### Whole-rock plotting

First-class plot families:
- TAS and alkaline/subalkaline classification where valid;
- Harker diagrams;
- Mg# and compatible-element screening;
- REE and multi-element normalized patterns;
- isotope plots where meaningful;
- literature comparison using the same source visibility controls as mineral plots.

### Series/group workflow

A rock must be usable both as an individual sample and as part of a series:
- dyke swarm;
- massif/complex;
- lithological group;
- publication/reference series;
- user-defined work group.

Group visibility and style must reuse the common plot styling system.

### Provenance

Each composition/isotope row keeps source/method/laboratory metadata. Bulk import must never collapse incompatible duplicates silently.

## Acceptance tests

- the workspace opens a sample and exposes all linked objects without navigation loss;
- whole-rock + literature filtering uses source controls consistently;
- an individual sample can be excluded from a series plot without deleting it;
- sample aliases do not break mineral links;
- whole-rock trace elements keep units and do not mix wt.% and µg/g;
- all current rock-regression tests remain green.

# Shared architecture

## Immutable selections

All three workflows use exact identity lists rather than labels where possible:
- analysis ids for analytical points;
- rock ids for whole-rock samples;
- image ids / generated source ids for figure panels.

Display names are metadata, not identity.

## Recipe model

Each publishable output must be reproducible from a versioned JSON-compatible recipe.

Common recipe fields:
- `recipe_version`;
- `kind`;
- selected object ids;
- ordering;
- layout;
- styles;
- journal preset;
- output settings.

## Implementation order

1. panel label sequence and normalized-position model;
2. add labels to existing scientific multi-panel plots;
3. generic raster publication composer engine;
4. Streamlit publication-composer page;
5. routing from `Подготовить рисунок / таблицу` and publication sidebar;
6. recipe export and regression tests;
7. project-image adapters.

### v0.15.3
1. profile data model/order engine;
2. profile plotting backend;
3. UI mode and exact-selection routing;
4. zones/reverse/normalization;
5. image-linked traverse foundation;
6. tests.

### v0.15.4
1. rock workspace read model;
2. overview and data-health cards;
3. series/group filters;
4. integrated whole-rock plots and literature comparison;
5. provenance/interpretation tabs;
6. regression and UI tests.

## Definition of done

A version is not done because the UI renders. It is done only when:
- exact-selection regressions are green;
- Windows CI is green;
- export regression is green;
- no new workflow silently guesses identity or missing chemistry;
- user-facing navigation exposes the feature through a natural task path.
