# Правила разработки ПетроЛаба

Цель этих правил — чтобы научные расчёты, база данных и интерфейс оставались проверяемыми и редактируемыми по мере роста проекта.

## 1. Язык и именование

- Пользовательский интерфейс, сообщения и пользовательская документация — на русском языке.
- Имена Python-модулей, функций, классов и переменных — на английском языке.
- Научные обозначения (`SiO2`, `Mg#`, `apfu_Fe3`) сохраняются в принятой предметной форме.
- Имена должны описывать назначение. Не использовать `tmp`, `data2`, `func1`, `new_df` вне очень короткой локальной области.

## 2. Архитектурные границы

- `app.py` — только запуск приложения, конфигурация Streamlit, навигация и композиция UI.
- `petrolab/ui/` — страницы и переиспользуемые UI-компоненты Streamlit.
- `petrolab/services/` — сценарии приложения: импорт, синхронизация, экспорт, работа с изображениями.
- `petrolab/db.py` и будущий `petrolab/repositories/` — хранение и выборка данных.
- `petrolab/minerals/` — чистая предметная логика минералогических расчётов; никакого Streamlit и файлового UI.
- `petrolab/plotting.py` и связанные модули — построение фигур и подготовка графических данных; UI не должен быть обязательной зависимостью.
- Чистая функция не должна читать глобальное состояние Streamlit, менять файлы или писать в БД.

Это целевая структура. Переход к ней выполняется постепенно небольшими PR без одновременной переписи всего приложения.

## 3. Размер и читаемость

- Одна функция должна решать одну задачу.
- Ориентир для функции — до 40–60 строк. Более длинная функция требует явного обоснования.
- Ориентир для обычного модуля — до 400–500 строк.
- `app.py` постепенно сокращается до примерно 100–150 строк.
- Повторяющаяся логика выносится в функцию или сервис после второго устойчивого повторения, а не копируется третий раз.
- Вложенность глубже 3–4 уровней считается сигналом к декомпозиции.

## 4. Типы и контракты данных

- Все публичные функции получают type hints.
- Нетривиальные публичные функции получают короткий docstring: что принимают, что возвращают и какие гарантии дают.
- Метаданные анализа (`_analysis_id`, `_dataset_id`, `_source_row`) не изменяются пользовательским редактированием.
- `_analysis_id` — стабильный идентификатор точки и не должен меняться при перечитывании связанного Excel, если точка сопоставлена с прежней строкой источника.
- Функции не должны неожиданно изменять переданный `DataFrame` на месте; если мутация нужна, она должна быть очевидна из API.
- Смешанные типы в столбцах, предназначенных для Streamlit/PyArrow, нормализуются до отображения.

## 5. Научные расчёты

- Формула или алгоритм не меняются в рамках «чистого рефакторинга».
- Любое изменение минералогического метода сопровождается:
  1. ссылкой на методику/источник в коде или документации;
  2. тестом на известный состав либо опубликованный пример;
  3. отдельным описанием того, что именно изменилось в результате.
- Отсутствующий аналитический столбец и измеренный ноль — разные ситуации, кроме случаев, где методика явно допускает нулевое значение для отсутствующего компонента. Такое допущение документируется и тестируется.
- Нельзя «чинить» научный результат только ради прохождения теста.

## 6. Безопасность научных данных

- Реальные Excel/CSV, изображения и SQLite-базы не коммитятся в GitHub.
- Исходный XLSX/XLSM никогда не перезаписывается без резервной копии.
- Обратная запись разрешена только в исходные колонки, для которых сохранено отображение на Excel.
- Ошибка синхронизации не должна приводить к ложному сообщению об успешной записи.
- Деструктивные операции требуют явного пользовательского действия.

## 7. Ошибки и исключения

- Не использовать пустой `except:`.
- `except Exception` допускается на границе UI, где ошибка превращается в понятное сообщение пользователю; внутри предметной логики ловятся конкретные исключения.
- Ошибка должна либо обрабатываться полностью, либо пробрасываться выше. Нельзя молча терять исключения.
- Текст ошибки для пользователя должен говорить, что произошло и что можно сделать дальше.

## 8. Windows и кодировки

- Основная пользовательская платформа сейчас — Windows.
- Все `.bat` содержат только ASCII и сохраняются с `CRLF`.
- Пути всегда заключаются в кавычки.
- Python-файлы и Markdown — UTF-8.
- Для путей используется `pathlib.Path`, а не ручная сборка строк через `\\` или `/`.

## 9. Git и изменения

- `main` должен быть запускаемым.
- Функциональные изменения и рефакторинг выполняются в отдельных ветках.
- Один PR — одна связная задача.
- Рефакторинг не должен одновременно менять научный смысл расчётов.
- Коммиты небольшие и называются по результату: `Extract dataframe utilities`, а не `fix stuff`.
- Перед слиянием PR обязательны зелёные автоматические проверки.

## 10. Тесты

Минимальный набор перед слиянием:

- компиляция всех Python-файлов;
- регрессионные тесты минералогических формул;
- core smoke-test SQLite/Excel/изображений/рецептов;
- Streamlit UI smoke-test основных страниц;
- проверка `.bat` на ASCII и `CRLF`.

Каждый найденный баг по возможности сначала превращается в воспроизводимый тест, затем исправляется. Тест остаётся в репозитории как защита от возврата ошибки.

## 11. Зависимости

- Новая библиотека добавляется только если она заметно упрощает или улучшает функцию проекта.
- Перед добавлением проверяются лицензия, поддержка Windows и необходимость зависимости.
- Критичные UI/API-зависимости фиксируются достаточно строго, чтобы внезапный релиз не ломал приложение.
- Устаревшие API удаляются после появления предупреждения, а не после фактического удаления из библиотеки.

## 12. Definition of Done

Изменение считается готовым, когда:

1. код читаем без знания истории чата;
2. поведение описано именами и короткими комментариями там, где это действительно нужно;
3. нет известных предупреждений, появившихся из-за этого изменения;
4. тесты покрывают исправленный баг или новый критичный сценарий;
5. Windows CI зелёный;
6. пользовательские данные не попали в репозиторий.
